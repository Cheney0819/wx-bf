# RC9 精准捕获健壮化设计

## 目标

RC9 在不引入跨启动后台续跑的前提下，提高精准捕获在云电脑、登录期数据库重建、大库、取消和底层 Windows API 异常场景下的正确性、性能与收尾可靠性。

RC8 的单一入口、四个观察点、DPAPI pending 票据、证据门禁语义和原子输出结果保持不变。RC9 分成两个可独立验证的阶段：RC9.1 修复确定性的等待、句柄、模块校验和调试收尾问题；RC9.2 把“全部数据库预先完整快照”改成“监听期轻量探测、解除附加后逐库一致导出”。

## 方案选择

考虑过三种方案：只修局部性能问题；在现有一次性流程内分阶段重构；直接实现跨启动持久化监听。RC9 选择第二种。

只修局部问题无法解决登录后数据库新建或换代造成的漏库。直接实现持久化监听会同时引入后台生命周期、状态迁移和跨启动恢复，超出本轮范围。分阶段重构可以先消除确定性缺陷，再用可回退的方式替换数据库数据流。

## 全局约束

- 不恢复旧内存扫描或 30 秒兼容检查。
- 不增加第二个恢复入口。
- 不实现程序关闭后的后台监控，也不自动开始下一轮捕获。
- 不降低模块 SHA-256、观察点签名、SQLCipher 页 HMAC、SQLite `integrity_check` 或原子输出要求。
- 允许导出 key、DPAPI 明文、捕获 payload、数据库源文件或调试内存。
- RC8 发布目录和文件哈希保持不变，RC9 使用新的发布目录。
- 工作区没有 Git 元数据，以测试、格式检查、产物哈希和独立审查作为检查点。

## RC9.1：等待与调试链路加固

### 空 PID 与句柄查询

`ProcessFileHandleFinder.FindProcessIdsHoldingFile` 明确区分三种输入：

- `candidatePids == null`：允许全局查询，仅供明确调用者使用。
- `candidatePids.Count == 0`：立即返回空集合，不调用 `NtQuerySystemInformation`。
- 非空集合：只处理集合内 PID 的句柄。

精准捕获始终传入显式候选集合，因此未发现目标进程时不会扫描系统句柄。句柄路径查询不再为每个句柄创建一个可无限积累的 `Task.Run`。实现使用有固定并发上限的查询执行器；任一原生路径查询超时后停止本轮所有者探测并退回普通 PID 顺序，不影响精准捕获主流程。超时工作单元数量受固定上限约束，后续刷新不会无限增加挂起线程或句柄。

### 模块身份与签名

新增一次捕获尝试内的模块检查结果，键由规范化路径、文件长度和最后写入时间组成。一次检查完成以下工作：

1. 流式计算 DLL SHA-256。
2. 解析 PE 头和节表。
3. 只读取每个观察点需要的签名字节。
4. 再次检查文件标记，确认检查期间模块文件没有被替换。

同一文件代际只进行一次完整顺序读取。多个观察点不再分别 `ReadAllBytes`。文件代际发生变化时丢弃缓存并重新验证，不复用旧身份结果。

### 可取消附加

`TryAttach` 接收 `CancellationToken`。每次附加尝试前检查取消，重试间隔使用可取消等待，不再使用不可取消的 `Thread.Sleep`。用户取消后，除正在执行的单次 Win32 调用外，不再额外等待完整的 5 秒重试周期。

### 断点恢复

断点恢复改为返回结构化结果，不再静默忽略失败。每个观察点按以下顺序收尾：

1. 写回原字节。
2. 刷新指令缓存。
3. 重新读取目标地址，验证原字节已经恢复。
4. 短暂重试，必要时重新打开进程句柄。

目标已经退出时按“无需恢复”收尾。目标仍存活且原字节无法验证时，操作进入明确的致命收尾状态，不报告成功或普通取消，也不把该会话记作干净解除附加。调试恢复循环继续到原字节恢复或目标退出；界面持续显示恢复状态和具体 PID，避免用户误以为已经安全完成。

## RC9.2：当前代数据库探测与逐库导出

### 数据模型

原 `DatabaseCaptureTarget` 不再持有完整数据库 `byte[]`。它改为持有轻量描述符：

- 规范化数据库路径。
- 当前文件代际标记。
- 文件长度和当前 16 字节 salt。
- 与长度兼容的 profile 集合。
- 少量加密抽样页。
- pending key、抽样命中信息和全页认证状态。

抽样页沿用现有第 2 页、第 1 页、中间页、末页策略。每个目标只保留这些页，而不是完整数据库。

### 捕获前

按钮开始时进行数据库路径发现和轻量描述符读取，不再调用 `StableDatabaseSnapshot.Read` 读取全部数据库。读取描述符时记录文件代际；发生变化则短暂重试。单个无法读取的非选中库仍可跳过，选中库失败仍阻止开始并给出明确错误。

### 监听期刷新

在当前一次捕获会话内，监听循环定期刷新已知数据库目录，并在处理捕获候选前执行一次快速刷新：

- 新出现的 `.db` 加入目标集合。
- 长度、salt 或文件代际变化的未确认目标替换为当前描述符。
- 已确认目标不被无条件覆盖；若导出时发现代际不一致，则重新进入待验证状态。
- 已删除文件标记为本轮不可用，不阻断其他库。

这属于本轮监听的动态发现，不保存跨启动后台任务。

### key 命中处理

观察点命中时，原生事件线程只读取寄存器、复制最多 4096 字节的候选、写入有界敏感数据通道、恢复观察点并继续调试事件。数据库发现、文件读取和密码学运算不在调试事件线程执行。

通道容量固定为 64 个候选，单个候选不超过 4096 字节。消费者在目标进程继续运行后完成快速目录刷新、候选规范化和当前描述符抽样页 HMAC 验证。通道已满时不静默丢弃 key；本轮记录结构化 `CandidateQueueOverflow`，完成观察点恢复并安全解除附加，提示用户重试。通道完成或取消时，尚未消费的全部候选必须清零。

命中的 raw key 复制到可清零的 pending 缓冲并关联数据库路径；消费后的候选对象立即清零。抽样匹配不执行全库读取、WAL 合并、全页认证、SQLite 打开或输出写入。所有标准化候选无论是否提前命中都必须在同一作用域内释放，避免未枚举候选残留敏感缓冲。

### 解除附加后的逐库处理

每轮监听解除附加后，只处理具有 pending key 的数据库，并且一次只处理一个：

1. 获取主库与 WAL 的一致代际。
2. 将 checksum 连续、已提交的 WAL 覆盖流式构造成随机临时加密快照。
3. 逐页验证 HMAC，并同时把已验证页面解密到原子输出临时文件。
4. 运行 `integrity_check`。
5. 原子移动为最终 `.readable.sqlite`。
6. 删除临时加密快照，清零页缓冲和 key，释放该目标。

全页认证失败时删除所有临时输出，保留当前会话内的 pending key，并用最新轻量描述符重新验证；只要监听时间仍有剩余，就继续监听后续 key 事件。一个库失败不阻断其他已命中库。

### 内存与磁盘边界

- 内存不再与全部数据库总大小成正比。
- 数据库和 WAL 使用固定大小缓冲，解密输出逐页写入。
- 同时最多存在一个库的临时加密快照和一个原子输出临时文件。
- 临时文件使用随机名称，所有成功、失败和取消路径都执行清理。
- 单文件 2 GB 的 `byte[]` 上限随完整内存快照一起移除；实际文件上限由 SQLite 页号、可用磁盘和文件系统决定，并在开始导出前检查剩余空间。

## 取消与错误处理

- 进程等待、模块等待、附加重试、描述符刷新、WAL 快照、逐页认证、解密、写入和完整性检查都传递同一个取消令牌。
- 取消先停止新增工作，再恢复全部观察点并解除附加，最后删除当前临时文件和清零敏感缓冲。
- 已经原子完成的输出保留；尚未移动的临时输出删除。
- 单库文件变化、WAL 换代或输出失败记录为逐库失败，继续处理其他库。
- 调试器状态、断点恢复和进程句柄错误属于会话级错误，立即停止新增数据库工作并进入安全收尾。
- 错误判断使用结构化错误类别，不再依赖中文或英文错误字符串包含关系。

## 组件边界

### ProcessFileHandleFinder

只负责候选 PID 内的文件所有者优先级。失败时返回空优先级和诊断，不决定捕获成功或失败。

### ModuleInspectionCache

负责一次捕获尝试内的模块身份、PE 映射和观察点签名结果。它不写目标进程内存。

### DebugCaptureBackend

只负责附加、观察点、寄存器读取、向有界通道复制候选、事件继续和可验证收尾。数据库发现、密码学验证和输出不进入原生事件循环实现。

### CapturedCandidateChannel

负责调试事件线程与候选消费者之间的有界所有权转移。写入成功后通道拥有候选；读取成功后消费者拥有候选；写入失败、取消和通道清理都必须清零对应缓冲。通道溢出是结构化会话错误，不允许静默丢弃。

### DatabaseProbeCatalog

负责数据库轻量发现、代际识别、抽样页读取和动态增删。它不持有完整数据库内容。

### MultiDatabaseCaptureCollector

负责候选标准化、抽样匹配、pending key 生命周期和匹配状态。它不执行完整数据库解密。

### ConsistentDatabaseExporter

负责单库 WAL 一致快照、全页认证、流式解密、`integrity_check` 和原子输出。它在完成一个库后释放全部单库资源。

## 性能验收指标

- 没有目标进程时，等待循环不调用系统句柄枚举。
- 单次模块代际最多进行一次完整 DLL 顺序读取。
- 监听期内不分配与数据库总大小相当的托管数组。
- 导出峰值托管缓冲为固定页/流缓冲，不随数据库文件大小线性增长。
- 正常可取消阶段在收到取消后 1 秒内进入调试收尾；原生调用卡住或断点恢复失败时显示明确状态。
- 调试事件线程不访问数据库文件或执行密码学验证；Windows 压力测试记录每次事件从收到到 `ContinueDebugEvent` 的耗时。

## 测试设计

### RC9.1 自动测试

- 空候选 PID 不调用系统句柄查询。
- 非空候选只检查允许的 PID。
- 句柄路径查询并发和超时工作单元数量有固定上限。
- 模块多观察点验证只进行一次完整读取，文件代际改变会使缓存失效。
- 附加重试可在等待期间取消。
- 原字节写回、缓存刷新和回读验证顺序正确。
- 写回失败、目标退出和重开句柄分别产生正确的结构化收尾结果。
- 候选通道所有权、容量、溢出、取消和未消费缓冲清零均有测试。

### RC9.2 自动测试

- 捕获开始不读取任何完整数据库数组。
- 描述符读取期间文件变化会重试或报告逐库失败。
- 登录期新建数据库可被动态加入并由后续候选命中。
- 登录期同路径数据库被替换后，旧描述符失效，候选使用新 salt 和新抽样页。
- 未命中数据库不会触发完整 WAL 快照或解密。
- 数据库刷新和抽样匹配运行在候选消费者，不运行在调试事件线程。
- 多个标准化候选提前命中后，全部候选敏感缓冲仍被清零。
- WAL 换代、页 HMAC 失败、磁盘空间不足、输出占用和取消都不留下临时文件。
- 多库处理中一个库失败不阻断其他库完成。
- 使用大于可用测试内存的稀疏夹具验证流式路径不会分配整库数组。

### Windows 真机测试

- 未启动目标程序等待 5 分钟，观察 CPU、线程数和句柄数保持稳定。
- 先点捕获，再启动并登录，覆盖数据库新建、截断、替换和 WAL 持续写入。
- 在进程等待、模块等待、观察点已设置、key 命中、WAL 快照和输出写入阶段分别取消。
- 同时存在主进程和辅助进程时验证 PID 优先级与跳过逻辑。
- 注入断点恢复首次失败，确认重试、回读验证和界面状态。
- 使用接近真实规模的大库记录峰值工作集、模块验证耗时、捕获事件暂停时间和总导出时间。

## 发布门槛

1. RC9.1 独立完成全部自动测试和 Windows 取消/收尾测试后，才开始 RC9.2。
2. RC9.2 必须保持现有 Release 测试全部通过，并新增上述代际变化与流式处理测试。
3. 运行 warnings-as-errors、`dotnet format --verify-no-changes`、Windows x64 自包含发布和 PE 身份检查。
4. 独立静态审查重点检查资源释放、取消、临时文件、敏感缓冲、Win32 句柄和错误分类。
5. 新建 `dist/refactor-rc9/`；ZIP 只包含 RC9 EXE 和中文测试步骤，并生成 SHA-256。
6. RC8 EXE、ZIP 和哈希必须保持原样。

## 明确不做

- 不实现关闭程序后继续监听。
- 不实现跨启动的未命中数据库任务队列。
- 不自动重启目标程序或自动登录。
- 不并行附加多个 PID，也不并行解密多个数据库。
- 不修改语义导出模块的数据结构和导出格式。
